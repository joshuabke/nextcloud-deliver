# Deliver v2 — Spec

Milestone: **0.2.0** (first working release of the rewrite; 1.0.0 is App Store submission).
Vocabulary: [CONTEXT.md](../CONTEXT.md). Decisions with lasting consequences: [docs/adr](./adr).

## Problem Statement

Editors deliver cuts to clients and colleagues and need frame-accurate feedback on them. Frame.io does this well but is a paid SaaS that copies the media out of the editor's own storage; Clapshot is self-hosted but a separate silo with its own uploads and users. Editors who already keep their material in Nextcloud want the review to happen where the files already are: the cut lands in a synced folder, everyone who may see the folder can comment, outsiders get a link, and the comments come back into the NLE as markers. The existing Deliver 0.1.x prototype does not deliver that: comments are tied to share tokens and vanish with them, anyone with a link can edit anyone's comment, password protection is a stub, the frontend stack is end-of-life, and the player lived inside the Files sidebar, which never worked well.

## Solution

Deliver becomes a proper Nextcloud app, rebuilt from scratch, in which media files in Files are enabled for review: an enabled file becomes an Asset, in a Project or in No Project, and a whole folder can become a Folder Project on Auto Intake so that every media file in it counts. Projects collect files from anywhere without moving them (ADR 0009). Iterations of a cut form a Version Stack, and Members (whoever Files lets open the file) and Reviewers (whoever opens a Review Link a Member made) leave Comments anchored to Frames or Ranges. Browser-unfriendly sources get Proxies, Thumbnail Strips and Waveforms generated by ffmpeg in the background when ffmpeg is available. Comments export as EDL, FCP7 XML, FCPXML or CSV per Version. Members get Nextcloud notifications, Reviewers get a Personal Link that keeps their identity forever. Reviewing outsiders arrive through Review Links, Deliver's own review links for a whole Project or picked Assets (ADRs 0010 and 0011); sharing in Files stays plain Nextcloud sharing. Files stays the source of truth; Deliver stores only review state.

## User Stories

### Projects and Assets

1. As a Member, I want to enable a single video or audio file for review from the Files sidebar, in a Project I pick there or in No Project, without its folder becoming a Project, so that only the cuts I pick become Assets.
2. As a Member, I want to make a folder I can write to a Folder Project with one button in the Files sidebar, with Auto Intake on unless I switch it off first, so that every media file in it, including the ones that arrive later through the sync client or an upload, becomes an Asset without another click.
3. As a Member, I want switching Auto Intake off to keep the Assets it collected and hand the per-file choice back to me, so that the two ways of enabling never fight over one folder.
4. As a Member, I want to take a single file out of Deliver after a confirmation, so that its review data is cleaned up while the file itself stays.
5. As a Member, I want the Deliver app page to list every Project I can access, so that I have one place to find reviews.
6. As a Member, I want a Project to show its folder tree with every enabled file as an Asset, so that subfolders keep their meaning.
7. As a Member, I want a Project to have a default frame rate, so that undetectable videos still get frame-accurate Comments and audio can be read in the Project's timecode.
8. As a Member, I want a Project to have a timecode display setting (SMPTE, frames, seconds), so that every viewer sees the format my team works in.
9. As a Member who may change a Project, I want to delete it after a confirmation, refused while it holds an Asset I may not change, it going to Deleted Projects whole instead of being lost at once, so that a finished job leaves the list and a slip costs nothing (stories 148 to 152, ADR 0015).
10. As a Member, I want a folder inside a Folder Project to be refused as a new Folder Project, so that Auto Intake never fights over a file.
11. As a Member, I want a Folder Project whose folder was deleted to lose its folder and Auto Intake but keep its Assets, so that trash restore and a new home keep my comments.

### Versions

12. As a Member, I want a file named `cut_v3.mp4` that arrives when exactly one Asset `cut` exists to be stacked automatically as Version 3, so that my sync-client workflow needs no browser visit.
13. As a Member, I want to be notified when an automatic stack happens and to undo it with one click, so that wrong guesses cost nothing.
14. As a Member, I want ambiguous filename matches to be offered as a suggestion instead of applied, so that two candidates never get merged silently.
15. As a Member, I want to stack any two Assets of the same kind of media by hand and set each Version's Version Number, so that naming conventions are never mandatory.
16. As a Member, I want to unstack a Version back into its own Asset, so that mistakes are reversible.
17. As a Member, I want to drop a file onto an Asset in the Deliver UI and have it uploaded into the same subfolder and stacked as the next Version, under its Version Number (`mix.mp3` as `mix_v2.mp3`) where a file of its name is there already, so that delivering a new cut is one gesture and never fails on a name.
18. As a Member, I want a Version whose file went to trash to show as Missing with its Comments intact, and to be notified, so that nothing is lost by accident.
19. As a Member, I want a Version whose file was permanently deleted to be removed together with its Comments, so that Deliver does not accumulate ghosts.
20. As a Member, I want a moved or renamed file to stay the same Version in the same Project, wherever it goes, so that reorganising folders is free.

### Playback

21. As a Member or Reviewer, I want to play a Version in the browser with frame stepping (arrow keys and `,` `.`), J/K/L shuttle, buttons and Shift+arrows that skip ten seconds, space, loop of a Range and playback speed, and to click on the timeline without stopping playback (dragging along it, with a mouse or a finger, seeks live, holds playback and resumes on letting go), so that I can inspect any frame.
22. As a Member or Reviewer, I want the current position shown as SMPTE timecode or frame counter according to the Project setting, and audio-only Versions as `m:ss.mmm`, with a session-local toggle between them, so that I can read it the way I think.
23. As a Member or Reviewer, I want every Comment as a circle on the timeline, and its Ranges on it, so that I see where the feedback is and seek there.
24. As a Member or Reviewer, I want hover thumbnails on the timeline and a waveform under it, so that I can find a moment quickly, especially in audio-only material.
25. As a Member, I want to see "processing, N %" while derived media is generated and to play the original meanwhile if the browser can, so that waiting is transparent.
26. As a Member or Reviewer, I want a clear "not playable in this browser" message for sources without a Proxy on installs without ffmpeg, so that I know why nothing plays.
27. As a Member or Reviewer, I want seeking to be frame-exact at the Version's frame rate and start timecode, so that my Comment lands on the frame I meant.

### Milestone 1.1: Takes

Classical recordings are made in Takes: many passes over the same passages, partly over the whole work, partly over a few bars. The producer and the musicians choose between them by listening to the same place in several Takes, one after the other. Today that means a copy of the recording session for everyone. With 1.1 the recording session delivers its Takes into a Take Folder (reaper-deliver does it in one click, ADRs 0008 and 0012), and anyone the folder is shared with compares them in the browser.

## Implementation Decisions

### Repository and stack

- A rewrite from scratch. Nothing from 0.1.x is inherited; the EDL generator and any useful test ideas are re-read, not copied.
- Backend: Nextcloud app framework, PHP 8.2+, minimum Nextcloud 33: the Files sidebar tab is a web component registered through `@nextcloud/files` (`getSidebar().registerTab`), which exists from 33 on, and @nextcloud/vue 9 needs 31 or newer anyway; older releases are end of life. Frontend: Vue 3, @nextcloud/vue 9, Pinia, Vite via @nextcloud/vite-config. English source strings with `t()`, German translation shipped.
- App id stays `deliver`, author Joshua Böke, repository github.com/joshuabke/nextcloud-deliver.
- Versioning restarts at 0.2.0. No signed release workflow yet.

### Domain model and persistence

Files is the source of truth (ADR 0002). Deliver's tables hold only review state:

- **Project** (ADR 0009): name, folder file id (nullable; set for a Folder Project, which takes the folder's name), owner user id (who made it), Auto Intake flag (Folder Projects only), default fps, timecode display mode, created at, deleted at and by (a Deleted Project, ADR 0015), what newcomers start with (as in Files, View or None) and whether files in review are locked (ADR 0018). Only made on purpose: by name, or from a folder (Auto Intake on). Folder Projects do not nest. Who belongs to it is derived per request from access to each Version's file; Deliver stores only the Access levels a Member with Manage set (ADR 0016).
- **Project Member**: Project id, a user id or a group id, Access level (none, view, comment, manage), Share and Approve. Only for those whose level or switches differ from the default; a person's entry wins over their groups'.
- **Project Member seen**: Project id, a user id or a group id, and the newcomers setting in force when Deliver first saw them as a Member (view, none, or null for as in Files). A change of the setting applies only to those not yet seen; when it changes, everyone who is a Member and was not seen before is noted first with the setting they came under, and nobody is given an entry. Noted only then, never while reading, and removed with the Project, the account or the group, or once they no longer reach any of the Project's files while someone still does (whenever its Members are listed and in the hourly scan; with no file to be found at all, nobody is forgotten), so that gaining access again makes them newcomers under the setting of that day; an entry a Member with Manage set stays. A person with no entry of their own has the highest level and every switch across their groups, each at its entry or, if it is noted, where it stands, whether or not they are noted themselves, and across their own default as well unless one of those groups has an entry: a group's entry can lower its members, a group's note never lowers anyone below their own default.
- **Asset**: project id (nullable: No Project), enabled by (user id, for No Project), display name (derived from the newest Version's filename unless overridden), parent folder file id. An Asset exists for a file a Member enabled, or for every media file in a Folder Project's folder while Auto Intake is on and no Project holds it; removing it from its Project (from Deliver, in No Project) deletes the Asset with its Versions and Comments after a confirmation. Removing it marks every Version's file that lies in a Folder Project's folder as removed there, by file id, whichever Project held the Asset, so it survives renames, moves inside the folder, overwrites and Auto Intake being switched off and on; the mark goes with the file or when a Member adds it for review again. Assigning an Asset to a Project, or to none, moves no file. When a folder becomes a Folder Project, the Assets of No Project with a file in it join it.
- **Version**: asset id, file id (unique: a file is one Version at most), Version Number (integer, unique per Asset), delivered by (user id, nullable), overwritten at (nullable: Comments made before it are marked), media metadata (fps as rational, drop-frame flag, start timecode in frames, duration in frames, width, height, has video, has audio), state (ready, missing, purged), derived-media state per kind (none, queued, running, ready, failed with message).
- **Comment**: version id, parent comment id (nullable, one level), author reference (user id or reviewer id), in frame, out frame (nullable), body, resolved flag, created and updated timestamps. Frames are stored at the Version's fps; seconds are never persisted. An audio-only Version counts in milliseconds: its frame rate is 1000/1 whatever the Project's, so a Frame is a millisecond, its Frames never change meaning with the Project setting, and Takes line up to the millisecond (ADR 0007). Shown as timecode or frames, its position is converted to the Project's frame rate for display only. A Broadcast WAV's time reference becomes its start timecode.
- **Reviewer**: Project id (nullable for No Project), owner user id (on No Project the Member they belong to; on a Project only who invited them, or whose link they named themselves on, nothing checks it, and it is empty once that account is gone, ADR 0017), name, email (nullable), created at, removed at (nullable). Whether their address is in a Member's address books is not stored: it is asked of the address books of whoever lists the Reviewers, each time, as every Member of a Project lists them. A contact is never tied to a Reviewer: a changed or deleted contact changes nothing but that answer. A Reviewer is on the Review Links they were invited through, put on or named themselves on, and has a Personal Link through each of those and through no other (ADRs 0013, 0014). A Personal Link is the link's URL plus the key of that Reviewer on that link; each link they are on has a key of its own. Reviewers are never deleted while they have Comments: removing one marks them removed and takes them off every link, so their Personal Links stop working and they leave every list while their Comments keep the name; deleting a Review Link does not touch them, and a Member can issue a fresh Personal Link for an existing Reviewer under a new Review Link. Their own rights over a link's (comment, comment on older Versions, Watermark) are kept per link they are on, null leaving each to the link; an email address is one Reviewer per Project, whichever Member invites them (ADRs 0014, 0017).
- **Review Link**: Project (null: No Project), owner user id (the Member who made it, whose reshare rights bound what it shows; every Member with Share manages it, ADR 0017), token, label, description, password hash (`IHasher`), expiry date, the picked Assets (none: the whole Project; on No Project at least one, and an Asset leaves the link once it joins a Project), flags for comments, older Versions, Watermark, download, only the newest Version and paused. Removed with its Project (ADRs 0010 and 0011).
- **Link activity**: token, Reviewer (nullable), what happened (opened, viewed a Version, downloaded it), Version, time. Kept per token.
- **Seen state**: per person (user id or reviewer id) per Version, the timestamp up to which Comments have been on screen. Everything created after it is Unseen.
- **Project mute**: per user id per project, or for No Project.
- **Job**: kind (probe, proxy, thumbnails, waveform), version id, state, progress, attempts, stderr tail, timestamps. One table for background jobs and the optional worker; designed so an external worker can claim rows later without a schema change (ADR 0003).

File identity is always the Nextcloud file id, so renames and moves are free and never change a Version's Project. A move to trash sets the Version to Missing and notifies; permanent deletion purges Version and Comments. A Folder Project whose folder is deleted becomes a plain Project. Attachments live in app data under the Comment; one person's on one Version add up to the admin's limit (20 MB unless changed), counted with the new file in, so that uploads at the same moment cannot pass it together.

Nextcloud hands a deleted account's user id to the next account created under it, so a deleted account leaves nothing tied to its id: a Folder Project it made passes to whoever owns the folder, any other Project it made is deleted for good at once (story 152), the Review Links it made and the Project Member entries set for it go, its Reviewers on No Project are removed, while the Reviewers of a Project stay with it, their inviter forgotten, and its Comments, Approvals and Reactions stay, by a Deleted user that nobody can edit. A removed Reviewer stays removed.

A group id is given again the same way, so deleting a group removes its Project Member entries, and a group later created under the id starts as anyone newly given access does.

### Discovery and stacking

- A file listener plus a periodic scan job keep Assets in sync. While Auto Intake is on, every new video or audio file in the folder that no Project holds and no Member removed from it becomes an Asset with Version 1 unless the filename convention matches; otherwise files become Assets only when a Member enables them, and the listener merely follows moves, renames and deletions of the files already enabled. The scan checks every Version's file by id, wherever it lies.
- Convention parser: base name plus a suffix of the form `_v3`, `-v03`, ` v3`, `V3` (case-insensitive, optional separator, optional zero padding) before the extension. If exactly one Asset with that base name and the same kind of media exists in the same folder and the same Project (or No Project), the file is stacked automatically at that Version Number (or next free number on collision), and the Version carries an undo mark until a Member takes note. Otherwise nothing is stacked and the app page offers the candidates for one click; the offer is derived from the Assets on screen, never stored, so it cannot go stale.
- A Version Stack holds one kind of media: video, audio or stills. The container may change from Version to Version (a cut as .mov, then as .mp4), but a mix never joins a cut of the same name: automatic stacks, the offered candidates and stacking by hand all keep to the kind, and the file picker for a new Version offers only that kind.
- Stacks are always explicit rows; renaming a file never regroups anything.
- Drop upload in the app writes the file into the previous Version's folder through the normal Nextcloud upload endpoint and then stacks it explicitly. A file Auto Intake stacked there by its name meanwhile carries no undo mark: the Member chose it.
- A new Version's file does not fail on a taken name ("Upload a new Version", a drop on a Version Stack, "Upload a new cut") and never overwrites: where its name is taken, it gets the Version Number it will have, read from the server at that moment (`mix.mp3` becomes `mix_v2.mp3`), in place of a version suffix it already has (`cut v03.mov` becomes `cut v04.mov`), and where that name is taken too, the next free number, up to a hundred of them; after that it is refused. A name that is free stays. When another file takes the name while the bytes go up, the upload goes on under the next free one: chunks on the server are joined there rather than sent again, except on an object store that takes chunks as a multipart upload, which joins them only for the name they were sent for, so a retry sends them anew. Going on after a reload and retries keep the name an upload took. After a lost answer, or when its chunk folder is gone, a file under its name may be the upload itself, so this attempt is refused, neither given another name nor taken for the upload. Trying again after that counts as a new upload under the next number, so the folder may then hold the file twice; where its chunk folder is gone, trying again is refused every time, and only dropping the file again is a new upload.
- Every upload in Deliver (upload button, drop on a Project, "Upload a new Version", drop on a Version Stack, "Upload a new cut") goes through one queue in the store, one file at a time, so it outlives switching views inside Deliver; a reload or a closed tab ends it, after the browser's warning. It uses Nextcloud's chunked upload v2 (`MKCOL` under `/remote.php/dav/uploads/<user>/`, one `PUT` per chunk of the size the server announces (`files.chunked_upload.max_size`, at least 5 MiB, at most 10000 chunks; 0 sends the file in one `PUT`), `MOVE` of `.file` with `Overwrite: F`, so an existing name still fails) through a small client of Deliver's own in `src/lib/`, not `@nextcloud/upload`, whose 1.x releases ship a Vue 2 upload picker with @nextcloud/vue 8 in the same module as the uploader (the Files app of Nextcloud 34 bundles a second Vue for it; 2.0 exists only as a stale release candidate), and not the uploader of `@nextcloud/files` 4, which chunks and retries but neither goes on after a reload, nor refuses an existing name, nor gives back the file id. A failed chunk is sent again with growing pauses, and an offline browser pauses the queue. Unfinished uploads (name, size, modification time, target, chunk folder) are kept in `localStorage`; picking or dropping a file that matches one goes on from the chunks the server still has, which Nextcloud keeps for a day after the last one. An upload goes on only in its folder and on its Version Stack, whatever name it has taken there. Every upload a tab sends has a record of its own there, touched as it goes, so every tab of Deliver shows it with its progress; finished uploads stay in a second list with their Version, so every tab and a reload show their Processing until someone hides them. A record older than a day is dropped, and one the tab sending it touched in the last half minute is left to that tab, so a second tab neither shows it as interrupted nor cancels it; a tab that goes away hands its record over at once. Once every byte is sent the upload is the server's and can no longer be cancelled, and a file that arrived but could not be enabled is only enabled again on a retry, not sent again. A `MOVE` whose answer is lost (a proxy giving up while the server joins a large file) asks for the target's file id before it tries again. The browser decodes Waveforms one at a time, during uploads as after them.

### Media metadata and derived media

- Probe order: ffprobe when present; otherwise Deliver's own container reader, which takes the frame rate, duration and start timecode from a MOV or MP4, the time reference from a Broadcast WAV, an MP3, a FLAC or an M4A (ADR 0012) and a FLAC's exact duration, as ffprobe does; otherwise the Project default fps and start 0. Audio-only Versions always count in milliseconds. Members can override fps and start timecode per Version, which re-anchors nothing (frames stay frames) but changes display and export.
- Proxy: one H.264/AAC MP4 at the source frame rate (VFR conformed to average), capped at the configured resolution measured on the short side (1080p is 1920×1080 and 1080×1920 alike), CRF around 20, the picture capped a tenth below the Proxy bitrate threshold with half a second of buffer so that sound and the encoder's overshoot stay below it for anything longer than a few seconds (a hardware encoder that goes above it is replaced by libx264 for that Proxy), one-second keyframe interval, faststart. Sources browsers play (H.264 8-bit 4:2:0 with AAC in MP4, VP8/VP9 in WebM; not AV1, which only recent Apple hardware decodes) always play as the original by default, at any size; they get a Proxy only when their bitrate (file size over duration) is above the Proxy bitrate threshold, an admin setting of 20 Mbit/s by default, as a lighter choice the player can switch to at the same Frame (ADR 0019). For every other source the Proxy is the only playable rendition.
- Proxies from the browser (ADR 0019): without ffmpeg, the browser of a Member with Manage that uploads a video needing a Proxy makes it while the master uploads, with Mediabunny's `Conversion` (WebCodecs, and `@mediabunny/prores` for ProRes), and hands it in once the Version exists: uploaded next to the Version's file under a name without a media extension, as for a replace, then `POST /versions/{id}/proxy` with its file id. The server checks it from its headers: H.264/AAC MP4 that browsers play, with sound where the original has it, within the Proxy resolution and not above the Proxy bitrate threshold (its size over its length), as many Frames as the original (its own count where its headers tell; WebM and MKV count none and their length includes the sound, so there within a fifth of a second of the probed duration), its length within half a Frame of its Frames at the original's rate. The probe of the original runs right then if its background job has not yet. A Proxy that does not fit is refused with the reason, the upload deleted either way; where it was a conversion, the Version's Proxy shows as failed with the reason, otherwise nothing changes, also not for a browser converting meanwhile. While converting, the browser reports its progress with `POST /versions/{id}/proxy/progress`, a running job of its own that counts towards no limit of the queue; after two minutes without a report the Proxy counts as missing again. The Managers are told that a browser has to make it, by notification and, unless they turned it off, by mail, only once the original has been read for two minutes and no browser is making it: none ever reported, as for a file from a sync client, its tab closed, or its Proxy was refused. While one reports, or the server takes its Proxy (for an hour at most, as a request that dies says nothing; one that fails ends it at once), they are not, and where its Proxy arrives they never are. Both need Manage and, for a conversion (`converted: true`), refuse while the server has ffmpeg or the Version has its Proxy, one by hand above all; without `converted` the hand-in takes a Proxy made by hand, with ffmpeg too, and replaces one there (ADR 0020). A tab whose report is refused stops converting. A Proxy the server makes later replaces it only through regeneration. Before an upload in Deliver the browser reads the file's headers with Mediabunny and refuses what it can neither play nor convert: a codec it cannot decode, which it names, a container whose Frames the server cannot read without ffmpeg (MPEG-TS), or no H.264 encoder in this browser (open-source Chromium) (where Mediabunny reads no such container, what the browser's `canPlayType` takes still goes up); the answer depends on the browser, as Safari decodes HEVC and Firefox may not. The conversion runs one file at a time, into a file of the browser's private file system (OPFS), the MP4 index reserved at its start (faststart) because the Frames are known, `@mediabunny/aac-encoder` (WASM, MPL-2.0) standing in where the browser encodes no AAC (Chrome on Linux, Firefox). Before it starts, Deliver deletes its leftovers there and checks `navigator.storage.estimate()` against the expected size, asking `navigator.storage.persist()` where that is short; without room the master uploads alone. The browser measures the Proxy it made (bytes times 8 over seconds) against the threshold and, when it is above, converts once more with a video target lowered by the overshoot and a margin, and fails with a message if it is still above. The Proxy keeps the original's average frame rate unrounded, and the browser counts its Frames and its length against the original before it uploads it; a failed upload or a cancel stops it and deletes it. Each file in OPFS is held under a Web Lock until it is handed in, so that clearing, on every start of the Uploads dialog and before each conversion, passes by what another tab still needs. The browser reports its progress every 5 seconds, also while the Proxy uploads; when the server answers that it is still reading the original, the browser uploads the Proxy again a little later, up to a minute. Deliver's page allows WebAssembly and workers from `blob:` in its CSP for that. The same hand-in serves two more ways. On the Asset card, a Member with Manage gets the browser's pass for a Version without its Proxy (none, failed, or a browser that stopped reporting) while the server has no ffmpeg, as "Make missing derived media in this browser" (see Derived media from the browser); `proxy` in the card's `derivedFromBrowser` says so. In the Files app, Deliver's script looks at the uploader's queue (`window._nc_uploader`, @nextcloud/upload 1.x) every second; for a video uploaded into a folder it asks once per folder `GET /folders/{folderId}/intake`, which names the Proxy settings when Auto Intake of a Folder Project above it takes the file in, the Member manages that Project and the server has no ffmpeg. Then the browser converts from the `File` it holds while the file uploads and hands the Proxy in once the upload finished and Auto Intake made it an Asset, its progress in a toast that stays and in Deliver's sidebar tab of the file. Both ask before a reload or a closed tab loses the Proxy. On all three ways the same pass that makes the Proxy also makes the Thumbnail Strip and the Waveform, so the original is decoded once: Mediabunny's `process` hooks of the `Conversion` see each picture at the Proxy's size and each piece of sound. The Thumbnail Strip has the server's grid (`DerivedMedia::runThumbs`: a picture every `ceil(length / Thumbnail Strip cap)` seconds, at most the cap, in a near square grid, each 160 wide and of even height, black where the grid has no picture), for each mark the last picture before half past it, as ffmpeg's fps filter takes them, as a WebP from the canvas, or a JPEG where the canvas encodes no WebP (Safari). The Waveform has the peaks at the rate of `src/lib/waveform.js` (ADR 0021) and is handed in once the original is read, after the Thumbnail Strip, as the server counts its duration in the Version's Frames. Both are handed in after the Proxy, whatever became of it: the Waveform with `POST /versions/{id}/waveform`, the Thumbnail Strip with `POST /versions/{id}/thumbs`, which needs Manage and takes it only for a read video without one and none on its way, checks that it is a WebP or JPEG of that grid (its spacing and count may be one off, as the browser measures the length itself) and writes the index itself. A server-made one wins and replaces it on regeneration. The Files app's pages (where `LoadSidebar` loads Deliver's script) allow WebAssembly and `blob:` workers in their CSP as well, and no other page. The tab that makes a Proxy estimates the time left from the encoder's percent over the time since the pass began, shows nothing before 3 % and 5 seconds or from 99 %, and begins again with the second pass at a lower bitrate; no server field carries it.
- Proxies handed in (ADR 0020): "Upload Proxy…" on the Asset card's menu, for a Member with Manage on a Version that gets a Proxy (the card's Version carries `takesProxy`: read, with a picture, and unplayable or above the Proxy bitrate threshold), uploads the picked MP4 next to the Version's file the way the browser's Proxy goes up (`uploadNextTo` in `src/lib/proxy.js`), then `POST /versions/{id}/proxy` with its file id and without `converted`, with and without ffmpeg; the card shows the upload's progress, the server's reason when it refuses it. Its checks are the browser's; a Version that plays as it is answers 409 "This Version plays without a Proxy". Whatever comes in through that call, from a browser or by hand, sets `proxy_handed_in` on the Version (migration 1020), a column rather than a marker in app data because every card and every queued job reads the Version row anyway. A Proxy handed in replaces one ffmpeg made, and one a browser converted; a job making one is deleted before the Proxy is stored, so the running job finds itself withdrawn (`DerivedMedia::guard`, also after it copied its file into app data under a name of its own and before that file takes its name) and gives up without a second go in software; a converting browser's next report is answered 409, so its tab stops, and its hand-in would be refused; `enqueue` queues no Proxy for a Version with a Proxy handed in, so neither a retry of a failed job nor anything else makes another. "Remove Proxy" on the card (`proxyHandedIn`) calls `DELETE /versions/{id}/proxy`, which deletes it from app data, clears the mark and sets the Proxy to none; with ffmpeg it queues a Proxy job at once, without one the card offers "Make missing derived media in this browser" again. A Version whose Proxy ffmpeg made answers 409. `forget` clears the mark with the derived media, so "Regenerate" and a file written again drop a Proxy handed in. File names get no special treatment.
- Thumbnail Strip: WebP sprite plus JSON index, roughly one frame per second, capped by the admin setting. Without ffmpeg, a browser that makes a Proxy draws the Thumbnail Strip in the same pass, in the same shape (ADR 0019), as WebP and, where the browser's canvas encodes no WebP (Safari), as JPEG: the server takes both, keeps a JPEG as `thumbs.jpg` beside the `thumbs.webp` it makes itself and serves it as `image/jpeg` under the same `thumbs` URL (a WebP, if both exist, wins); regenerating deletes either.
- Scrub Proxy (#169): every video Version gets one, with or without a Proxy, as a job after the probe: H.264 MP4 320 wide (never wider than the source, even height from its aspect), every Frame at the source rate, a keyframe a second, 250 kbit/s (at most 400 within half a second of buffer), no sound, `scrub.mp4` in the Version's app data, about 1.9 MB per minute. Always libx264 `veryfast`: at 320 wide the encode costs little beside decoding the original, and hardware encoders know only a constant quality that would not hold the bitrate. Scrub Proxy jobs run after every other kind in the queue, the newest Version's first, and hold up no other work: while only Scrub Proxies fill the cap of jobs at once, the other kinds start beside them. With ffmpeg the hourly `ScanProjects` queues one for ten video Versions without one, the newest first, whenever none is queued; without ffmpeg it queues none. Used only for hover previews, by the player's timeline and by the Asset card (the Project view and a Review Link's landing page) where it is ready, and for the Asset card's still where Nextcloud renders none, else the Proxy or the original as before; served to Members through the derived-media route and to Reviewers through the link's, also where the link hides downloads, as it shows no more than the Thumbnail Strip does. It goes with regeneration and with a file written again, like all derived media. Without ffmpeg a browser hands one in through `POST /versions/{id}/scrub` (needs Manage), uploaded next to the Version's file as a Proxy is and deleted either way; the server takes an H.264 MP4 that browsers play, at most 320 wide, below 0.5 Mbit/s, with the Version's Frames within the tolerance of a Proxy, and needs no sound.
- Derived media from the browser (#168): without ffmpeg, the pass of the browser that uploads a video, in Deliver and through the Files app's hook alike, makes the Thumbnail Strip, the Waveform (from its sound; none without) and the Scrub Proxy of every video, and the Proxy only where it needs one, in one decode; a server-made one still wins, and no other Member's browser decodes a video by itself. With a Proxy the pass is the `Conversion` above, whose `process` hook also draws each picture at 320 wide into a canvas of its own that a second encoder (Mediabunny's `CanvasSource`, H.264, 250 kbit/s, a keyframe a second, the original's Frames at its rate, MP4 index reserved in OPFS) takes, so no full-size picture waits in it. Without a Proxy the pictures and the sound are decoded side by side (`VideoSampleSink`, `AudioSampleSink`) for the strip, the peaks and the Scrub Proxy only, each let go of once seen; that needs a picture this browser decodes in a container whose Frames the server reads, but no H.264 encoder, so a browser without one still makes the strip and the Waveform. A Thumbnail Strip or Scrub Proxy that fails, or a Scrub Proxy without room in OPFS, never fails the pass, nor does the Proxy: without room for it the pass runs without one, and one whose track would be left out, whose Frames come out off, or that is above the threshold on the second go (`verdict`) is left out, the rest handed in all the same, and the Proxy shows as failed with its reason. The browser checks the Scrub Proxy's Frames and that it is below 0.5 Mbit/s before it uploads it. After the Proxy, whatever became of it, the Scrub Proxy goes up next to the Version's file (`.deliver-scrub-…`) and in with `POST /versions/{id}/scrub`, then the Thumbnail Strip and the Waveform; the Scrub Proxy and the Thumbnail Strip have the server read the original in the request when its background job has not yet, and wait up to a minute while a worker reads it. A conversion whose Proxy hand-in is answered 409 because a Proxy by hand or ffmpeg came first shows as stopped, not failed. What a Version lacks is the server's rule, `DerivedMedia::fromBrowser`, as `derivedFromBrowser` on the card's Version and on every Version of `GET /versions/{id}`: without ffmpeg, for a read video whose Proxy no browser makes right now, the kinds among `proxy` (`DerivedMedia::proxyFromBrowser`), `thumbs`, `waveform` (with sound) and `scrub` that it lacks. The Asset card's "Make missing derived media in this browser" replaces "Make Proxy in this browser": for a Member with Manage where that list is not empty, offered once this browser has read the headers of what the card plays (the Proxy where there is one, else the original) and can make something of what is missing (`offer` and `passOf` in `src/lib/proxyPlan.js`), otherwise it says why; where only the Scrub Proxy is missing and this browser cannot make it (no H.264 encoder: Firefox or Safari without one, open-source Chromium), the entry is left out instead of a disabled one on every older card. The check is read again whenever what the card plays or what the Version lacks changes. The tab whose upload is still in its own pass offers no entry for that Version (`passing` in the uploads store); other tabs may, as a pass without a Proxy leaves no mark on the server: one would need a job kind or column of its own with a lapse like the Proxy's progress, and the cost of a second pass is a decode whose hand-ins are answered 409. It reads the Version again, decodes the lightest file there is (`lightest`: the Proxy, generated, from a browser or by hand, else the original) over range requests and makes only what is missing, its progress on the card as "Derived media" where it makes no Proxy. After a Proxy by hand is taken in Deliver without ffmpeg, the same action runs from the file this browser still holds, silent where nothing is left to make or this browser cannot; through the API nothing follows.
- Waveform: peaks JSON computed from raw PCM via ffmpeg, no extra binaries. Generated for every Version with audio. Its peaks come at a fixed rate (ADR 0021): `{"rate": 50, "peaks": "<base64>"}`, one byte a peak (0 silence, 255 full scale, linear), peak i the loudest sample from i / rate to (i + 1) / rate seconds into the file, at most 2 000 000 peaks; 1 hour is 240 KB, 10 hours 2.4 MB. The rate is 50 unless the file would go past 2 000 000 peaks (past 11 hours), then `max(1, min(50, floor(2000000 / ceil(seconds))))`; every producer applies the same rule. ffmpeg renders the sound at 16 kHz in all its channels (counted by ffprobe) and streams it into PHP, which keeps the loudest sample over all channels a share at a time, so sound on one side or out of phase counts and only the peaks stay in memory; a WAV is read from its PCM at its own rate over all channels in pieces of at most 512 KiB (at most 1 GiB in all, so past an hour of 24-bit stereo each share is read in part), and a header whose rate would make more peaks than a Waveform has is not read; the browser keeps the loudest sample over all channels and grows its peaks as it decodes, leaving out sound whose time is off. The hand-in takes up to 2 000 000 peaks at the rate of the Version's own length once it is read (a video not read yet is read in the request first; one with a frame rate but no length counts the duration handed in in its Frames; audio not read yet in milliseconds) and leaves out peaks past that length. The timeline's whole length draws an overview of at most 2000 buckets, each the loudest of its peaks. Waveforms from before the fixed rate counted as missing once (migration 1021): with ffmpeg whoever works the queue (cron or the worker) makes them one at a time, the newest Version first, whenever nothing else is queued, and opening a Version, as a Member or a Reviewer, queues its own Waveform ahead of them, so the Review view shows it in that visit; a Waveform made while idle that fails pauses that work for an hour across cron runs and workers (app config `idle_waveforms_after`), as its cause may be no Version's (storage offline), while one whose file is not there at all is left as none, not failed, and stepped past at once, twenty at most a run, the look going on below it the next time and from the newest again once past the oldest; a track without a sample gets a Waveform without a peak; without ffmpeg the browser ways below remake them. With ffmpeg, the first audio file a request brings (Files, a sync client, Deliver's upload, delivering again; one of a sync client's bulk upload or an unpacked archive, whose others go to the queue; never a folder taken in at once, as making a Folder Project, switching on Auto Intake, opening a Project with loose files or the hourly scan do) is read and gets its Waveform in that request, so its Waveform is there when its upload is, while on a plain install the queue waits for the next cron run and then behind every Proxy queued before (ADR 0022). Only a file on local, unencrypted storage of 1 byte to 256 MB, of at most 30 minutes, at no more bytes a second than 192 kHz 32-bit stereo PCM, runs there (ffmpeg needs about 3 seconds an hour of MP3); ffprobe and ffmpeg run for at most 15 seconds each, ffmpeg reads no further than its header's length and 5 seconds, and no more requests than `max_jobs` run one at once, counted apart from the queue; whatever is left goes on in the queue, and nothing of it fails the upload. The jobs are claimed in the table as a worker claims them, and a request's claim is queued again after 5 minutes should the request die. Longer audio and every video wait in the queue, where probes come first and then the Waveforms of audio, before the other kinds (a video's reads the whole master and keeps its place); the cron job runs at every cron run (an interval of a minute, as five minutes missed every other run of a cron every five minutes). A Review view, a Member's or a Reviewer's, asks the server again every 10 seconds while a Version's derived media is queued or made and also before its file is read (unless it went missing before), so a Waveform that becomes ready shows without a reload. Without ffmpeg, a WAV's peaks are read from its PCM on the server. The delivering tool hands in the peaks it has right after the upload. Other audio is decoded by the browser that uploads it, from the file it still holds, for drop uploads in Deliver and uploads in the Files app alike, so nobody downloads it for that; failing that, once by the first Member's browser that opens it. Either hands peaks and duration to the server (`POST /versions/{id}/waveform`, also before the probe ran, the duration then in milliseconds as for all audio). Neither overrides a Waveform the server made, and one the server makes later replaces theirs (ADR 0012). The uploading browser starts decoding while the file uploads and hands the peaks in once the Version exists. Both browsers decode in a stream: Mediabunny (pure JavaScript, MPL-2.0, loaded only when a Waveform is decoded) reads the packets from the file (`BlobSource`) or from the server with range requests (`UrlSource`) and WebCodecs' `AudioDecoder` decodes them, so only the peaks stay in memory and the progress is known; where the browser cannot decode the codec, `decodeAudioData` on the whole file remains.
- Loudness (decision A5): measured from the Version's sound and stored with its Waveform as `loudness` in the served Waveform JSON: `{"integrated": LUFS or null, "peak": dBTP or null}`, each to a tenth; `integrated` is null where every 400 ms block lies below the absolute gate (silence), `peak` null without a sample. With ffmpeg, a job of its own (kind `loudness`) follows each Waveform ffmpeg makes for an upload, a Version opened or a regeneration, never one the queue remakes while idle (old files are not read a second time for their loudness): ffmpeg's `ebur128=peak=true` reads the sound at its original rate over every channel (weighting the surrounds of 5.1 and 7.1, leaving out the LFE; `framelog=verbose` under `-v info`, which ffmpeg 4.4 and 5.1 know as well and which prints no frame lines there) and its summary gives the integrated loudness (BS.1770-4, gated at −70 LUFS and −10 LU) and the true peak in dBTP, which are written into the Waveform's JSON (under a name of its own first, so the file changes whole and its ETag with it); a run stopped early prints no summary and gives no numbers rather than those of a part. It is a job of its own because it costs more than the Waveform: an hour of stereo MP3 takes about 5 s for the Waveform and about 23 s more for ebur128 with true peak (12 s without true peak, 7 s for a sample peak alone by `astats`), so in the Waveform's run it would more than double the time an audio upload waits and halve what its own request can draw (ADR 0022). The job comes last in the queue, after Scrub Proxies and after the Waveforms the queue remakes while idle, and like Scrub Proxies holds up no other work: while only such jobs fill `max_jobs`, the other kinds start beside them. One that gives no numbers (ffmpeg fails, no summary) ends quietly, leaving the Waveform without them and no failed job; the summary is read from its `Summary:` line on, as the file's own tags come before it, and a track without a sample has no peak. A view that has loaded the Waveform before shows the loudness once it loads it again (opening the Version again); nothing asks again only for it. Without ffmpeg, the browser that decodes the Waveform as a stream, from an upload or the Asset card's pass or the first Member opening audio, measures it in the same pass from the same samples with `loudnessMeter` in `src/lib/loudness.js` (K-weighting for the stream's sample rate, 400 ms blocks every 100 ms, both gates, the channel weights of 5.1 and 7.1 by position) with the true peak in dBTP after BS.1770-4 Annex 2 (decision A9): each channel oversampled 4× by the Annex's 48-tap filter (Table 1) below 96 kHz, 2× (two of its four phases) from 96 kHz, not at all from 192 kHz, keeping only the filter's last 11 samples across pieces and skipping a piece whose loudest sample, times the filter's largest gain (about 2), cannot reach the peak so far; never below the sample peak. The meter runs in a Web Worker of its own (inlined as a `blob:` worker, which Deliver's pages and the Files app's allow; decision A10): the decode loop posts each piece's channels to it, their buffers transferred once the peaks are taken, at most eight pieces on their way before the loop waits for the worker's acknowledgement (a message, never a timer, so a hidden tab is not held back), and the worker answers at the end; where no worker can be made, the meter runs on the page as before. The browser hands it in with the Waveform, leaving it out (but not the Waveform) where a number would be past the server's ranges, as that means a broken decode; a browser that decodes the whole file at 8 kHz measures none. Without ffmpeg the server reads a WAV's peaks from its PCM but no loudness (no DSP in PHP), so the browser that uploads a WAV, in Deliver or in the Files app, reads it piece by piece from the file it holds (`wavLoudness` in `src/lib/wav.js`: integer PCM of 8, 16, 24 or 32 bits and float of 32 or 64, WAVE_FORMAT_EXTENSIBLE too, as the server's reader takes them, the first `fmt ` chunk counting as there, anything else left out; 65 536 frames a piece, never the whole file; an extensible WAV's channels weighted by its `dwChannelMask`, the LFE 0, back and side surrounds 1.41, any other 1, so a mask naming neither (stems, say) weights every channel 1 rather than as 5.1, and a plain WAV of 6 or 8 channels as 5.1 or 7.1; a cancelled upload stops the reading and ends the worker) and hands in the loudness alone, `POST /versions/{id}/waveform` with `loudness` and no peaks (decision A9). What a browser measured is bound to the content it measured: the uploading browser sends the ETag its upload came back with (`etag`), with a loudness alone and with a Waveform it decoded from its upload, and the server refuses the hand-in (409) where the file was written again since (Nextcloud keeps the ETag over a rewrite within the same second of the mtime, so that one slips through); the rewrite dropped what was stored, as always. The first Member opening audio decodes it over range requests and has no ETag to send, so that hand-in stays unbound. The server takes it only without ffmpeg, for a WAV, once: it is kept beside the Waveform (`loudness.json` in the Version's app data) and written into it by the same atomic rewrite the loudness job uses, at once where the Waveform is there, else when the server has read it; the server's Waveform wins (ADR 0012). `loudnessFromBrowser` on the Asset of a file says when; no later Member decodes a WAV for it. The hand-in's `loudness` is taken only from whoever may write the Version's file (peaks are a picture any Member who sees it may hand in, loudness a claim people act on: from anyone else the peaks are taken and the loudness left out, a loudness alone refused), optional and checked (integrated −70 to +15, peak −200 to +12; ffmpeg's numbers likewise, one past its range dropping the whole measurement as a broken decode; numbers or null, both keys there and no other, a hand-in with a `truePeak` or a missing key refused with 400: loudness is never taken without its true peak, so no sample peak in dBFS, decision L1). A Waveform without it shows no loudness; nothing is made again only for it, regeneration makes it. Shown only, never applied to playback (decision A1).
- Failed Processing is started again per Version by a Member with write access to its file through the regeneration of story 80 (`POST /versions/{id}/regenerate`, which also clears the failed jobs); without ffmpeg there is nothing to retry. Whether the server has ffmpeg reaches the app page as initial state, for the formats in the Uploads dialog.
- Captions (#54): an SRT or WebVTT file per language and Version, added by a Member with Manage through "Add Captions…" on the Asset card of a video. The browser checks it first (`.srt` or `.vtt`, at most 1 MB, at least one cue), uploads it next to the Version's file under a hidden name without a media extension (`.deliver-captions-…`), as for a Proxy from the browser, and hands it in with `POST /versions/{id}/captions {fileId, language}`; the server checks it again, reads it as UTF-8 (a byte order mark dropped) or, where it is no valid UTF-8, as Windows-1252, refuses it when not a single cue timing can be read, and deletes the upload either way. It stores the text as UTF-8 in `appdata_deliver/captions-<version id>/<language>.srt` or `.vtt` (WebVTT when it starts with `WEBVTT`), apart from the derived media, so that regenerating and rewriting the file keep it; a new file of a language replaces the old, `DELETE /versions/{id}/captions/{language}` removes one, and they go with the Version. The language is a BCP 47 tag, from the file name before the extension where it names one the browser knows, otherwise picked in the dialog from common languages, named in the user's language (`Intl.DisplayNames`). Every Version payload, the Review Link's included, lists `captions` with each language's URL through the media endpoint (`captions-<language>`), with the same access as the Version's derived media. The player (not Compare) offers them under a CC button, off by default, on phones in its settings menu. It fetches the chosen file and converts it in `src/lib/captions.js`: SRT becomes WebVTT (its timing lines with a period, its numbers as cue identifiers, coordinates dropped), WebVTT stays as it is with its cue settings; when the Version's start timecode is above 0 and no cue starts more than half a Frame before it, every cue moves back by it. The start timecode counts as media time, its Frames over the true rate (01:00:00:00 is 3600 s at 25 fps and 3603.6 s at 23.976), as Resolve and Premiere time the cues they export; the half Frame takes in a first cue written cut to the millisecond. The result plays as a `<track>` from a `blob:` URL, which the CSP of the app page and the review page allows as media. Display only: no editing, burning in or export.
- Storage in `appdata_deliver/<version id>/`. Served through a range-capable streaming endpoint for both Members and Reviewers.
- Jobs run in Nextcloud's background job system, one ffmpeg at a time by default, with the optional `occ deliver:worker` loop and `occ deliver:regenerate`.
- Admin settings: ffmpeg path, ffprobe path, max parallel jobs, max resolution, the Proxy bitrate threshold (2 to 200 Mbit/s), thumbnail cap, hardware encoder with device path (probed on save), extra ffmpeg args, the default place for Project folders, the attachment limit per person and Version, plus a read-only status panel. A save checks every value before it stores any.

### Takes

- Start in the file (ADR 0012): the delivering tool writes each file's Session Time into its tag under the name `DELIVER_TIME_REFERENCE`, the value the first sample's position in samples since midnight at the file's own sample rate, as decimal digits. It is read like a Broadcast WAV's `time_reference` and becomes the start Frame in milliseconds. Anything but 1 to 15 digits, or a tag over 4 KiB, is ignored and the start stays 0.
  - MP3: an ID3v2 tag (v2.3 or v2.4), as a TXXX frame with the description `DELIVER_TIME_REFERENCE` (ISO-8859-1, UTF-8 or UTF-16 with a byte order mark).
  - FLAC: a Vorbis comment `DELIVER_TIME_REFERENCE=<digits>`; the key is case-insensitive, as all Vorbis comment keys are.
  - M4A (MP4 audio): an iTunes freeform atom `----` in `moov/udta/meta/ilst`, with the mean `com.apple.iTunes`, the name `DELIVER_TIME_REFERENCE` and the digits as UTF-8 data. QuickTime `keys` metadata, as ffmpeg writes it, is not part of the contract.
- Take alignment rests on start Frames, which for audio are milliseconds, so Takes line up to the millisecond whatever the Project's frame rate. Playback position itself is continuous.
- Delivering again: a file written again in place (Files app, sync client, WebDAV `PUT`, a delivering tool, restoring an older file version) keeps its file id, Version and Comments, and Deliver re-reads it as on intake: what the probe found and all derived media go, a Waveform handed in for the old content too, so the delivering tool hands its peaks in again after the upload; a media job still running on the old content writes nothing back. Replacing the file of a Version that has Comments is the exception and needs an explicit confirmation: Deliver's own upload asks, and a delivering tool asks before it overwrites, after reading the Version's Comments through the OCS API; without the confirmation it delivers a new Version instead, or for a Take skips it (ADR 0008). A confirmed replace uploads the new content to a temporary file next to the Version's file, named without a media extension, and then calls `POST /versions/{id}/replace` with that file's id and the confirmation; inside its lock Deliver streams the content into the Version's file, keeps its id, deletes the temporary file and treats it as delivering again, noting `overwrittenAt` when the Version has Comments but telling nobody. Writes from the Files app or a sync client cannot be asked about; Deliver locks the file of a Version with Comments or Approvals so that they fail (ADR 0018), and where there is no lock they are taken as they come, the Comments marked as made before the overwrite.
- Take comparison: a view of its own over the Takes of one Take Folder, opened from the Project view, the Asset menu and a link's landing page, where a Take Folder is one entry. One audio element plays the selected Take; switching only happens while stopped. Comments are ordinary Comments on each Take's one Version (ADR 0008), anchored to a Frame; Ranges are not offered here.

### Permissions

- Which Assets a person sees follows each Version's file (ADR 0009); what they do with them is their Access level in the Project (ADR 0016), defaulting to read giving Comment and write giving Manage. Whatever touches a file (upload, rename, delete it) also needs write access in Files. The Project as a whole (its settings, its Members, deleting it) takes Manage there: by default write access to a Folder Project's folder, and on any other Project only the owner, while write access to a single file lets a Member manage that Asset. Someone with None gets 404 for the Project and its Versions, nothing is notified to them and they are not offered as a Mention.
- View: see the review. Notified and mentionable.
- Comment: everything above plus comment, reply, edit and delete own Comments. A Comment that someone else has replied to is deleted only with Manage, so nobody deletes another person's Reply along with their own Comment.
- Manage: everything above plus enable and disable files, assign them to a Project, stack and unstack (on both Assets), set Version Numbers, override metadata, resolve and unresolve, delete any Comment, regenerate derived media, export, the Project's settings and its Members' levels, never above their own.
- Approve (a switch, from Comment up): approve a Version or request changes. Share (a switch, offered where Files lets the Member reshare): make, change and delete the Project's Review Links and manage its Reviewers; a link shows only files the Member who made it may reshare (ADR 0010).
- The owner (the folder's owner for a Folder Project, whoever made any other Project) always has Manage, Share and Approve. A Folder Project's name follows its folder. No Project's links and Reviewers stay its Member's own.
- Reviewer (through a live Review Link): view, comment and reply when the link allows, edit own where the link allows comments, delete own always (with the same rule for Comments others replied to), download the original unless the link hides downloads, which hides the download buttons and the ZIP while the original still plays where no Proxy is made. A file the Member may only view in Files (a share without downloads) is never a download on their links either, as Nextcloud keeps it out of their reshares; where the admin allows no viewing without download, it is not on their links at all and its derived media stays closed to them, as Nextcloud hides its content. Never resolve, never see Assets the link does not show.
- Deliver never enforces a password of its own: it points out a review link without one, and an admin who wants the rule enforces it with Nextcloud's password policy, which applies to the passwords of Review Links as to Nextcloud's own.
- Sharing in Files makes an ordinary Nextcloud link: Deliver adds nothing to it, no Comments, no reviewer session (ADR 0011).
- A logged-in non-Member opening a Review Link becomes a Reviewer with the display name prefilled. A Member of a Version's file previews it on the link read only, as Reviewers see it, never as a Reviewer whose key the browser carries and without counting in the link's activity, with the way into the app view (story 59); Versions whose files they cannot open, and every Version of a Project where they have None, they review as a Reviewer.
- The public review route extends `AuthPublicShareController`, so the link's password prompt and expiry are enforced by core before Deliver runs. Deliver stores tokens and password hashes (`IHasher`) for its Review Links (ADRs 0010 and 0011); a Review Link shows only files its Member may reshare (`ProjectService::linkable`, for the link and the Project page alike). An external storage's "Enable sharing" option, off as `files_external` makes a storage, takes the share permission from its files, so they are on a link only once an admin switches it on; a storage on login credentials kept in the session cannot be opened in a link's request at all. The Project's Assets carry `offLinks`, whether the asking Member's links leave out the newest file, and for a Member with Share the Project counts them in a note above the Assets and marks each card.
- Reviewer sessions are a cookie per Review Link holding the key of the Reviewer on that link; it never expires. The Personal Link re-establishes it on any device, and a key that opens nothing on the link leaves the cookie as it was.

### API

One versioned REST surface under the app, used by the app page, the Files sidebar tab and the public review page alike, with two authentication modes: Nextcloud session for Members and link token plus reviewer key for Reviewers. Resources: projects, assets, versions, comments, Review Links, reviewers, exports, media streams, jobs, admin settings. A single `changes?since=` endpoint per Version returns new and changed Comments, Replies, resolves, and Version state so the client polls one thing every few seconds (backgrounded tabs poll slower). The design leaves room for notify_push later.

## Testing Decisions

A good test exercises Deliver the way a person or an NLE does and asserts on what they would see: HTTP responses, rendered UI, exported files, generated media. Tests never assert on private state, table rows, or which class was called.

Seams, from highest to lowest, with the intent to keep them to two:

1. **HTTP API inside a real Nextcloud** — PHPUnit integration tests booted with the Nextcloud test bootstrap in the dev container. Every backend story is tested here: permissions by acting as different users and reviewer keys, stacking by creating files through the Nextcloud filesystem, Missing and purge by moving and deleting files, exports by parsing the returned EDL/XML/CSV, derived media by running real ffmpeg on tiny fixture clips and asserting the resulting Proxy's fps and duration. Pure PHP units (timecode math, filename convention parser, EDL/XML writers) get plain PHPUnit unit tests as a second tier because they are cheap and precise.
2. **Browser via Playwright** against the dev container — the review flows: enable a file from the sidebar, open Review view, frame step and comment, Range comment, reply, resolve, badge on Unseen, Reviewer flow through a Review Link and a Personal Link on a fresh browser context, export download, sidebar tab. Vitest component tests are limited to pure client logic (timecode formatting, keyboard map, polling merge), not to component rendering.

Prior art in the repo is thin: two Jest component tests and a login-only Playwright spec from 0.1.x; they are references for tooling only. Fixtures: a 2-second 25 fps H.264 clip, a 23.976 fps clip, a ProRes clip, and a WAV, all under a second of audio, generated by ffmpeg in a setup script rather than committed.

CI runs php-cs-fixer, psalm, PHPUnit (unit and integration), Vitest and Playwright on every pull request that is no longer a draft and on every push to main, using a throwaway Nextcloud container with ffmpeg.

## Out of Scope

- Digest emails.
- Frame.io's project furniture: workspaces of Deliver's own, roles beyond the Access levels (ADR 0016), metadata fields (status, assignee, rating, keywords), cover images, and folder management inside Deliver. Nextcloud sharing and Files do those; Approvals and Due Dates carry the status.
- PDFs as Assets.
- Watermarks burned into the picture (the Watermark is an overlay in the player, and the link's settings say so).
- Adaptive streaming, multiple Proxy renditions, 4K Proxies.
- On phones: Exports, managing Version Stacks and upload by drag and drop; they stay on larger screens.
- External or GPU-farm transcoding workers over HTTP (job table is ready for it).
- Direct push of markers into DaVinci Resolve.
- Ranges, ratings and favourites on Takes; assembling Takes into a cut in the browser.
- Aligning Takes by their audio (they line up only as the recording session placed them).
- The Take comparison on phones.
- Deploying and running a particular Nextcloud server; the repo ships only a generic `deploy/` compose example with ffmpeg and `/dev/dri`.

## Further Notes

- VAAPI (Intel and AMD graphics) is the hardware encoder to verify first; software x264 remains the default everywhere.
- Frame anchors rely on the Proxy having exactly the source frame rate; this is a correctness invariant, not an optimisation.
- Ranges are inclusive of the out Frame.
- Comment sort default is by Frame with a newest-first switch; the Unseen badge exists precisely because Frame order hides recency.
- Timecode display mode is a Project setting for video; audio-only Versions and the Take comparison show `m:ss.mmm`. The player offers a session-local override between them that does not persist.
- Reviewer identity is permanent by design: a Personal Link is the credential. Members are told this when they create one so they hand it to one person only.
- Seeking keeps the playback state: a click on the timeline (and in the strip under an audio Waveform, or anywhere on Compare's lanes) jumps and goes on playing if it played, and a drag along the bar, by mouse or finger, takes the playhead along live (decision L3), holds playback and resumes on letting go if it played. Frame steps, the arrow keys and a click on a Comment in the list still pause.
- Skipping ten seconds (the buttons either side of Play on a desktop, entries of the ⋯ menu below 1024 px, audio and video, and Shift+← / Shift+→) converts the ten seconds to Frames at the Version's rate and keeps the playback state like any seek; a double tap by finger or pen on the left or right third of the picture, or of the scrolling Waveform, skips the same ten seconds, as does a double click on the Waveform (story 104; the double tap on Compare's Waveform too, both sides together, where a mouse click seeks). In Compare Shift+← / Shift+→ skip ten seconds on both sides together (keys only, no buttons there). Below 1024 px the controls are one row, upright and sideways: Play, the time and the length on the left, sound, the ⋯ menu and fullscreen on the right; the menu stays open while one skips or steps, and the time's format is chosen in it. Where the player is 345 px wide or less (its own width, not the window's, so beside the Comment list too) the length steps aside.
